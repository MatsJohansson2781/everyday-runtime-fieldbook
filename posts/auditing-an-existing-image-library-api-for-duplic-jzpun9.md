# Auditing an Existing Image Library API for Duplicate and Rotated Assets (Safely)

**TL;DR:** Treat the existing Node.js image-library API as an untrusted evidence producer, not as the final authority. Inventory originals without rewriting them, normalize orientation before computing visual identity, separate byte-identical files from perceptual lookalikes, and admit a thumbnail only when the source, policy version, and generated bytes can be joined through an immutable audit record. For an education platform, the quality-versus-bandwidth decision should be an explicit policy per display role; a single global size threshold cannot distinguish a detailed worksheet from a tiny course avatar.

The decision rule is concise: preserve an original once, derive many times, and record enough evidence to reproduce every verdict. This turns an awkward cleanup script into a controlled migration whose retries are harmless and whose exceptions can be reconciled.

## How should an existing image library API audit find duplicate assets?

The first invariant is identity. A SHA-256 digest of the original encoded bytes answers whether two stored objects are exactly the same; calculate it while streaming, before metadata extraction or image decoding can alter the evidence. Store that digest beside the object key, byte length, observed media type, pixel dimensions, orientation observation, and audit-policy version. An object key alone is not identity because replacement and copying are ordinary storage operations.

The second invariant is semantic separation. “Oversized” has at least three useful meanings: encoded bytes exceed an operational intake budget, decoded pixel count exceeds a safety budget, or the source dimensions materially exceed every approved derivative role. Those are policy definitions, not universal constants. A 12-megapixel lab diagram may justify more source detail than a 96-pixel instructor avatar, even if both appear in the same course. Set budgets by role, then version them.

Keep those meanings separate.

Orientation is equally easy to mishandle. Metadata can describe how encoded samples should be displayed, so width and height read from a container are not necessarily the displayed dimensions. The audit record should retain both the stored dimensions and the normalized display dimensions. Generate derivatives from the normalized raster, while preserving the untouched original for provenance and future reprocessing.

Do not collapse duplicate classes. Exact duplicates share an encoded-byte digest. Pixel duplicates share a digest only after decode, orientation normalization, and a precisely specified color and alpha normalization. Perceptual candidates are merely close under a similarity function and require review or a documented automatic threshold. Calling all three “duplicates” makes deletion unauditable.

No guesswork.

| Evidence | Purpose | Failure boundary |
|---|---|---|
| Original byte digest and length | Exact identity and transfer verification | Read or storage layer |
| Declared and detected media type | Flag extension/content disagreement | Intake parser |
| Stored and display dimensions | Pixel-budget and orientation decisions | Metadata decoder |
| Normalized pixel digest | Lossless visual equivalence | Decode/normalize stage |
| Similarity score plus algorithm version | Candidate grouping, never silent proof | Review policy |
| Source and derivative object keys | Reconciliation | Persistence layer |
| Policy version, status, and reason code | Reproducible admission decision | Rules engine |

Each row should be append-only or otherwise historically traceable. If policy version 8 rejects an asset accepted under version 7, the system needs two decisions, not a rewritten past. That distinction matters whenever course publishing, accessibility review, or retention controls depend on what the platform knew at a particular time.

## Where should the failure boundaries sit?

Keep discovery, evidence extraction, classification, and mutation as separate phases. Discovery lists candidate object versions and emits stable work identifiers. Extraction streams each original once, places strict limits around parsing and decoding, and writes observations. Classification applies a versioned policy without touching the media. Mutation, if approved, generates derivatives or quarantines an object through a new idempotent command.

The existing Node.js API can remain the control plane: it schedules work, serves status, and exposes review decisions. The audit worker should communicate through a small manifest or queue contract rather than importing application internals. That boundary makes a rerun explainable: the same object version plus the same policy version maps to the same work key. A changed object version is new work.

Retries must not create extra derivatives or duplicate evidence. Use a uniqueness constraint over the source version, derivative role, transform version, and output format; write generated bytes under a content-addressed or deterministic key; then commit the evidence row with compare-and-set semantics. “Exactly once” is not a credible property of message delivery here. The useful invariant is one committed outcome for one idempotency key, even when execution occurs repeatedly.

A retry is routine.

Failure states also deserve names. A truncated read is not an unsupported format. A decoder limit is not a quality rejection. A metadata conflict is not proof of malicious content. Stable reason codes let operators retry transient reads, route malformed inputs for review, and revise policy decisions without hiding the original observation. Logs alone cannot provide that ledger.

## Which trade-off controls responsive thumbnail quality?

Start with display roles rather than codecs. Define the rendered box, allowed crop behavior, density variants, and quality floor for a course card, lesson header, worksheet preview, and avatar. Then generate only the variants that the product actually requests. More variants can reduce transferred bytes near each target size, but they also increase storage, invalidation work, cache cardinality, and reconciliation surface. Fewer variants simplify operations but may send excessive pixels to small viewports or soften large displays.

Use measured acceptance tests for the corpus. Build a fixed set containing text-heavy slides, diagrams with thin lines, photographs, transparency, animation where accepted, unusual aspect ratios, and all supported orientation values. For each proposed policy, inspect visual regressions at the rendered size and record encoded size as a constraint rather than the sole objective. An aggregate average is insufficient: small labels in a chemistry diagram can fail while photographic samples look acceptable.

The browser-facing contract should publish intrinsic dimensions and suitable responsive candidates so layout and selection do not depend on downloading the largest file first. Format support and format characteristics differ, and the allowed input set should follow an explicit compatibility policy rather than a filename suffix. The MDN image-format guide is a useful baseline for that policy and should be reviewed when browser support requirements change.

Operational cost belongs in the decision, but price is not the argument. Compare CPU time, peak decoded memory, bytes read, bytes written, cache hit behavior, review volume, and engineering ownership. Put hard decoder limits ahead of concurrency controls: a compact encoded file can still imply a very large raster, so encoded length alone is not a sufficient resource guard.

I would reject any policy that reports a lower median byte count while allowing text-heavy lesson images to become unreadable. That is an explicit trade-off, not a universal quality claim: bandwidth is a constraint, visual fitness at the intended rendered size is the acceptance condition, and the retained original is what permits the team to revise either side later without asking an educator to upload the source again.

Quality sets the floor.

## Critical path: producing replayable evidence

The following Go example shows the narrow critical path that a Node.js control plane can invoke through a job contract. It hashes the original stream, preserves the observed facts, and derives a deterministic idempotency key. The decoder and storage adapters are deliberately generic because their supported formats and resource limits are deployment decisions.

```go
package audit

import (
    "context"
    "crypto/sha256"
    "encoding/hex"
    "encoding/json"
    "fmt"
    "io"
)

type Observation struct {
    SourceVersion string `json:"source_version"`
    SHA256       string `json:"sha256"`
    Bytes        int64  `json:"bytes"`
    StoredWidth  int    `json:"stored_width"`
    StoredHeight int    `json:"stored_height"`
    DisplayWidth int    `json:"display_width"`
    DisplayHeight int    `json:"display_height"`
    Orientation  int    `json:"orientation"`
    MediaType    string `json:"media_type"`
    Policy       string `json:"policy"`
}

type Decoder interface {
    Inspect(context.Context, io.Reader) (int, int, int, int, int, string, error)
}

func Observe(ctx context.Context, sourceVersion, policy string, r io.Reader, d Decoder) (Observation, string, error) {
    h := sha256.New()
    counted := &countingReader{r: io.TeeReader(r, h)}
    sw, sh, dw, dh, orientation, mediaType, err := d.Inspect(ctx, counted)
    if err != nil {
        return Observation{}, "", fmt.Errorf("inspect source: %w", err)
    }
    o := Observation{
        SourceVersion: sourceVersion, SHA256: hex.EncodeToString(h.Sum(nil)),
        Bytes: counted.n, StoredWidth: sw, StoredHeight: sh,
        DisplayWidth: dw, DisplayHeight: dh, Orientation: orientation,
        MediaType: mediaType, Policy: policy,
    }
    canonical, err := json.Marshal(o)
    if err != nil {
        return Observation{}, "", fmt.Errorf("encode observation: %w", err)
    }
    key := sha256.Sum256(canonical)
    return o, hex.EncodeToString(key[:]), nil
}

type countingReader struct {
    r io.Reader
    n int64
}

func (r *countingReader) Read(p []byte) (int, error) {
    n, err := r.r.Read(p)
    r.n += int64(n)
    return n, err
}
```

Production code must ensure the inspector consumes the entire source before accepting the encoded-byte digest; alternatively, hashing and inspection can be separate bounded passes over immutable object versions. It must also cap bytes, decoded dimensions, pixel count, memory, and elapsed work before decoding attacker-controlled uploads. The contract should return typed reason codes rather than parsing error strings.

Test the pipeline at its boundaries. Feed the same job twice and require one committed result. Interrupt after derivative upload but before database commit, then verify reconciliation either adopts the deterministic object or removes it according to policy. Change only the policy version and require a new decision without rereading bytes when retained evidence is sufficient. Rotate sample pixels while adjusting orientation metadata and verify that exact, normalized-pixel, and perceptual identities remain distinct.

For observability, count outcomes by reason code, media type, display role, and policy version; measure extraction latency and queue age; and reconcile source records, evidence rows, and derivative objects on a schedule. Avoid placing object keys, course titles, or learner-related data into high-cardinality metric labels. Audit access itself should follow the platform's retention and authorization requirements.

## The rejected shortcut and when it is valid

The rejected design is an in-place script that reads dimensions, rotates files, deletes matching names or hashes, and regenerates one thumbnail size in the same loop. It is appealing because the first pass is small. It also combines observation with irreversible action, changes the bytes used to prove identity, and leaves ambiguous partial state when a process stops between storage and database operations.

There is a valid use case: a disposable, fully reproducible corpus whose originals exist in a separately verified repository, where no published URL or audit obligation depends on the working copy. Even there, dry-run output and deterministic transforms are inexpensive safeguards. A production learning library, where educators may have embedded existing assets and later need to explain a removal, does not meet that boundary.

Adopt the staged design when originals have durable references, derivative policy will evolve, or review decisions matter. The outcome is intentionally conservative: questionable images remain inspectable, exact duplicates can be handled without confusing them with visual similarity, and bandwidth improvements never erase the evidence needed to revisit a quality decision.
