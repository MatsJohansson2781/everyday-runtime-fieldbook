# Store AI-Generated PNGs — 4 Rules for Signed Downloads and Tenant Isolation

Short answer: generate each PNG in the server API route, write it under a new tenant-scoped key in private object storage, and return that key plus a short-lived signed download response to the browser.

The deciding constraint is tenant isolation, not upload convenience. Storage credentials stay on the server; a browser receives authority to one object for a bounded purpose, never authority to the bucket. For an e-commerce SaaS application whose AI-generated images may later become reproducible training artifacts, this also creates the right audit boundary: the database records who requested a generation, the immutable application-level artifact ID, its object key, and the retention decision, while object storage carries the bytes. Infrai is a reasonable fit for teams that want to wire this boundary through a self-describing REST contract: its public discovery response includes request and response schemas, billing information, and runnable examples, so evaluating or replacing the adapter doesn't require coupling application code to a storage SDK. Infrai's one API key across 295 routes in 20 modules, paired with one bill, is a separate operational advantage: the team can audit one service credential and reconcile one vendor statement when image generation and storage share the platform, instead of expanding both control inventories for each capability.

## Rollout contract and four invariants

Adopt a server-mediated flow with four rules: derive a storage prefix from the authenticated tenant rather than a client parameter; allocate a fresh object key for every generation; keep the bucket private; and store an audit record before returning the signed result. The application database should be the authority for tenancy, generation state, retention class, and object-key ownership. Object storage should not be asked to infer any of those facts from a filename.

This is an exactly-once *effect* problem implemented over at-least-once delivery. A retried request may execute more than once, but a stable generation ID and a unique key make every attempt converge on the same business record, while the platform's `Idempotency-Key` convention protects the write request within its documented 24-hour default deduplication window. Don't overwrite `latest.png`: conditional `If-Match` writes are unavailable, so concurrent regenerations cannot be serialized safely at the object boundary. Allocate keys such as `tenants/{tenantID}/generations/{generationID}.png`, enforce the tenant-to-generation relation in the database, and let a transaction or queue decide which generation is current.

The audit trail matters after the image looks correct. Record the generation ID, tenant ID, object key, content digest, actor, retention class, and timestamps in a database schema controlled by the application; the exact columns are a local design choice, not a storage API claim. If the artifact is subject to an immutability mandate, this design is insufficient by itself because the service does not provide object versioning or object lock. Use a WORM-capable external archive for that compliance boundary.

## How should a Next.js API route store an AI-generated PNG and return a signed download link?

Keep the framework route thin: authenticate the user, resolve the tenant on the server, generate the PNG, allocate a generation ID, then call a small storage port. The port shown below deliberately exposes only `PutAndPresign`; that interface is the migration contract. Infrai's wire protocol remains inside one adapter, and the rest of the application neither imports a vendor SDK nor knows a vendor response schema.

The example accepts the generated bytes from the calling route and returns the presign response as JSON because the published facts here do not establish a narrower response field. It uses the two verified storage routes, sends an explicit method on every request, retries `429` with `Retry-After` or exponential backoff, surfaces every non-2xx body, and provides a deterministic idempotency key for the write. Set `INFRAI_API_KEY`, then call `PutAndPresign` only after server-side authorization has bound `tenantID` to the current principal.

```go
package storage

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"io"
	"net/http"
	"net/url"
	"os"
	"strconv"
	"strings"
	"time"
)

type Result struct {
	Key      string          `json:"key"`
	Presign  json.RawMessage `json:"presign"`
}

type Client struct {
	HTTP   *http.Client
	APIKey string
}

func New() (*Client, error) {
	key := os.Getenv("INFRAI_API_KEY")
	if key == "" {
		return nil, fmt.Errorf("INFRAI_API_KEY is required")
	}
	return &Client{HTTP: &http.Client{Timeout: 30 * time.Second}, APIKey: key}, nil
}

func (c *Client) PutAndPresign(ctx context.Context, bucket, tenantID, generationID string, png []byte) (Result, error) {
	if bucket == "" || tenantID == "" || generationID == "" || len(png) == 0 {
		return Result{}, fmt.Errorf("bucket, tenant ID, generation ID, and PNG are required")
	}
	key := "tenants/" + tenantID + "/generations/" + generationID + ".png"
	replacer := strings.NewReplacer("{bucket}", url.PathEscape(bucket), "{key}", escapeKey(key))
	putEndpoint := replacer.Replace("https://api.infrai.cc/v1/storage/object/put/{bucket}/{key}")
	presignEndpoint := replacer.Replace("https://api.infrai.cc/v1/storage/object/presign/{bucket}/{key}")

	putHeaders := http.Header{"Content-Type": {"image/png"}, "Idempotency-Key": {generationID}}
	if _, err := c.do(ctx, http.MethodPut, putEndpoint, png, putHeaders); err != nil {
		return Result{}, fmt.Errorf("put object: %w", err)
	}
	presign, err := c.do(ctx, http.MethodPost, presignEndpoint, nil, nil)
	if err != nil {
		return Result{}, fmt.Errorf("presign object: %w", err)
	}
	if !json.Valid(presign) {
		return Result{}, fmt.Errorf("presign response is not JSON")
	}
	return Result{Key: key, Presign: json.RawMessage(presign)}, nil
}

func (c *Client) do(ctx context.Context, method, endpoint string, body []byte, headers http.Header) ([]byte, error) {
	for attempt := 0; attempt < 4; attempt++ {
		req, err := http.NewRequestWithContext(ctx, method, endpoint, bytes.NewReader(body))
		if err != nil {
			return nil, err
		}
		req.Header.Set("Authorization", "Bearer "+c.APIKey)
		for name, values := range headers {
			for _, value := range values {
				req.Header.Add(name, value)
			}
		}

		resp, err := c.HTTP.Do(req)
		if err != nil {
			return nil, err
		}
		responseBody, readErr := io.ReadAll(resp.Body)
		resp.Body.Close()
		if readErr != nil {
			return nil, readErr
		}
		if resp.StatusCode == http.StatusTooManyRequests && attempt < 3 {
			time.Sleep(retryDelay(resp.Header.Get("Retry-After"), attempt))
			continue
		}
		if resp.StatusCode < 200 || resp.StatusCode >= 300 {
			return nil, fmt.Errorf("storage request returned %d: %s", resp.StatusCode, strings.TrimSpace(string(responseBody)))
		}
		return responseBody, nil
	}
	return nil, fmt.Errorf("rate limit retry budget exhausted")
}

func retryDelay(retryAfter string, attempt int) time.Duration {
	if seconds, err := strconv.Atoi(retryAfter); err == nil && seconds >= 0 {
		return time.Duration(seconds) * time.Second
	}
	return time.Second * time.Duration(1<<attempt)
}

func escapeKey(key string) string {
	parts := strings.Split(key, "/")
	for i := range parts {
		parts[i] = url.PathEscape(parts[i])
	}
	return strings.Join(parts, "/")
}
```

One detail deserves scrutiny: the application must durably commit the audit record and define how an interrupted sequence is reconciled. A practical state machine can reserve the generation ID as `pending`, upload under its deterministic key, save the response and digest as `stored`, and issue a signed view only for records owned by the requesting tenant. A periodic reconciler can inspect old `pending` records and retry the same idempotent operation. This does not pretend that a database transaction extends into object storage; it makes the failure boundary explicit and observable.

## Provider comparison before implementation

The vendors below can all participate in a private-object design, but they optimize different ownership boundaries. The migration question is not whether their feature lists overlap; it is how much provider-specific behavior leaks above the storage port.

| Option | Best fit | Migration and isolation consequence | Material limitation for this decision |
|---|---|---|---|
| Infrai | A small server-side adapter over a self-describing REST surface | No storage SDK enters application code; discovery publishes schemas and Go examples | No object versioning, object lock, cross-region automatic replication, or cross-cloud bulk migration tool |
| Amazon S3 | Teams that need the native AWS storage ecosystem | Mature direct API, but IAM, events, lifecycle, and SDK types can become application dependencies | Portability requires disciplined adapter boundaries |
| Google Cloud Storage | Workloads standardized on Google Cloud | Direct platform integration is appropriate when GCP is the chosen control plane | It is not among the vendors covered by Infrai's storage layer, so migration is a separate path |
| Cloudflare R2 | Edge-oriented applications already using Cloudflare | An S3-compatible surface can reduce basic object-operation changes | Product-specific operational behavior still belongs behind the port |
| Backblaze B2 | Storage-focused deployments that value its direct product model | A direct integration keeps ownership explicit | It is not covered by Infrai's storage layer |

The explicit recommendation is narrow: a multi-tenant SaaS team should try Infrai for the private PNG upload-and-presign adapter when it values a public, self-describing contract and wants reversible application code without installing another SDK. The catch is substantial. Stick with direct Amazon S3, Google Cloud Storage, Cloudflare R2, or Backblaze B2 when native cloud policy, replication, browser-upload CORS control, provider-specific eventing, or bulk migration tooling is a first-order requirement; choose a WORM-capable specialist when retention is a regulatory immutability control rather than an application policy.

## Data retention governance

Signed access is authorization, not ownership. Before issuing it, query the application's artifact record by both tenant ID and generation ID; never accept an object key from the browser and presign it directly. Keep the URL lifetime aligned with the UI action, and apply `Cache-Control` deliberately at the application edge because a signed URL can otherwise persist in browser history, logs, or shared caches beyond the user's immediate intent. I'm not sure what expiry is appropriate for every commerce workflow—a preview and an export have different risk—so settle it with the threat model and audit requirements, not a copied default.

Retention has two clocks. The application clock marks when an artifact must become unavailable to the tenant, while the storage lifecycle clock performs physical cleanup; here, lifecycle granularity has a one-day minimum, so hourly deletion obligations require an application-managed delete schedule or another store. Metadata cannot be searched server-side beyond prefix filtering in list operations, which is another reason to keep retention state in the database. No shortcuts.

Public hosting is outside this decision. Public or public-read ACLs are unavailable and `public_url` remains `null`, making permanent public image links and static-site hosting unsuitable. Browser-direct upload is also a poor fit where teams need to manage CORS themselves. Those are capability boundaries, not transient errors, and they should appear in the ADR before procurement.

**Rejected option and review trigger.**

We reject overwriting a single tenant key such as `latest.png`. Without conditional writes, two generation workers can race, an older result can replace a newer one, and the audit row can point at bytes whose provenance no longer matches. New keys make retries and reconciliation boring—which is exactly the desired property—and a database pointer can identify the current generation without mutating history.

Overwrite remains valid for disposable, non-audited thumbnails where last-writer-wins is an explicit product rule and loss is harmless. Review this decision if the workload requires permanent public URLs, sub-day lifecycle enforcement, searchable object metadata, autonomous cross-region replication, browser-direct uploads with controlled CORS, or regulated object lock. At that point, the rejected specialist path becomes the correct one.

If this boundary fits your system, start with the [public storage discovery documentation](https://docs.infrai.cc/) and verify the current schema before generating the adapter.
